# Tauri Application and IPC

## 1. Responsibility boundary

Tauri is the desktop control and presentation layer. It is not part of the PCM data path.

Tauri responsibilities:

- Window and tray lifecycle.
- Device and route configuration.
- User profiles and preferences.
- Start, stop, bypass, and reconfigure commands.
- Low-rate metrics, state, and error events.
- Permission explanations and platform setup guidance.

Rust audio-engine responsibilities:

- All CPAL streams.
- All sample buffers.
- All resampling and DSP.
- All DeepFilterNet inference.
- Route recovery and real-time metrics production.

## 2. Application state

```rust
pub struct AppState {
    pub engine: AudioEngineHandle,
    pub config_store: ConfigStore,
}
```

`AppState` must not contain:

- A DeepFilterNet processor.
- A CPAL callback buffer.
- An unbounded PCM channel.
- A mutex that callbacks need to acquire.

## 3. Command API

Recommended initial commands:

```rust
#[tauri::command]
fn list_audio_devices(
    state: tauri::State<'_, AppState>,
) -> Result<DeviceInventoryDto, ApiError>;

#[tauri::command]
fn refresh_audio_devices(
    state: tauri::State<'_, AppState>,
) -> Result<(), ApiError>;

#[tauri::command]
fn start_route(
    request: StartRouteRequest,
    state: tauri::State<'_, AppState>,
) -> Result<RouteAcceptedDto, ApiError>;

#[tauri::command]
fn stop_route(
    route_id: RouteId,
    state: tauri::State<'_, AppState>,
) -> Result<(), ApiError>;

#[tauri::command]
fn update_route_settings(
    request: UpdateRouteSettingsRequest,
    state: tauri::State<'_, AppState>,
) -> Result<(), ApiError>;

#[tauri::command]
fn get_engine_snapshot(
    state: tauri::State<'_, AppState>,
) -> Result<EngineSnapshotDto, ApiError>;

#[tauri::command]
fn save_profile(
    profile: AudioProfileDto,
    state: tauri::State<'_, AppState>,
) -> Result<(), ApiError>;
```

Commands should validate DTOs and enqueue bounded engine commands. They should not block until long-running route initialization completes. Return an acceptance response, then report state transitions through events or snapshot polling.

## 4. DTOs

Keep serializable frontend DTOs separate from internal runtime types.

```rust
#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
pub struct StartRouteRequest {
    pub route_id: String,
    pub source_device_id: String,
    pub destination_device_id: String,
    pub mode: ProcessingModeDto,
    pub target_latency_ms: u16,
    pub denoise: DenoiseSettingsDto,
}

#[derive(Clone, Debug, serde::Serialize)]
pub struct AudioDeviceDto {
    pub id: String,
    pub name: String,
    pub direction: DeviceDirectionDto,
    pub is_default: bool,
    pub available: bool,
}
```

Do not serialize backend-specific handles or assume that a user-facing device name is a stable identifier.

## 5. Events

Recommended event topics:

```text
audio://state-changed
audio://devices-changed
audio://metrics
audio://fault
audio://permissions-changed
```

Event cadence:

- State and fault events: immediately when generated by the control plane.
- Meters and queue metrics: approximately 10-20 updates per second.
- Full device inventory: only on refresh or change.
- Detailed timing histograms: on demand, not every frame.

Never emit one event per audio callback or model frame.

## 6. Frontend state model

Suggested stores:

```text
DeviceStore
  - inputs
  - outputs
  - defaults
  - lastRefresh

RouteStore
  - route configurations
  - route states
  - active faults
  - metrics snapshots

ProfileStore
  - saved profiles
  - current profile

AppStore
  - platform support status
  - permission status
  - onboarding state
```

Treat engine events as observations, not the sole source of truth. On frontend startup or reconnect, call `get_engine_snapshot` to reconcile state.

## 7. UI surfaces

### Main route screen

- Input-device selector.
- Output-device selector.
- Processing mode.
- Start/stop control.
- Bypass toggle.
- Noise-reduction controls supported by the adapter.
- Input and output meters.
- Current state and clear error banner.

### Diagnostics screen

- Negotiated source and destination formats.
- Model identifier and sample rate.
- Estimated latency.
- Input/output queue fill.
- Underrun, overrun, reset, and missed-deadline counters.
- Inference p95 and p99.
- Drift correction.
- Copyable sanitized diagnostic report.

### Routing setup screen

- Platform-specific virtual-device status.
- Detected virtual microphone or loopback endpoints.
- Clear instructions when external installation is required.
- Loop-detection warnings.

## 8. Persistence

Store only configuration, not runtime handles.

Example schema:

```json
{
  "schemaVersion": 1,
  "selectedProfileId": "default",
  "profiles": [
    {
      "id": "default",
      "name": "Default",
      "sourceDevicePreference": "stable-device-id-or-default",
      "destinationDevicePreference": "stable-device-id-or-default",
      "targetLatencyMs": 60,
      "denoise": {
        "enabled": true,
        "postFilterEnabled": true
      }
    }
  ]
}
```

Migrate configuration on application startup before creating routes.

## 9. Validation

Validate at multiple boundaries:

- Frontend: immediate usability feedback.
- Tauri command: authoritative DTO validation.
- Engine command handler: domain and current-state validation.
- Model adapter: exact range and capability validation.

Examples:

- Reject zero target latency.
- Reject an output device selected as a microphone source unless the route explicitly supports loopback.
- Reject a model setting unsupported by the loaded model.
- Reject attempts to start a route already in `Starting`, `Running`, or `Recovering`.

## 10. Security

- Configure Tauri capabilities with least privilege.
- Do not expose a generic command that opens arbitrary model paths.
- Do not pass shell commands from the frontend.
- Sanitize diagnostics before presenting or exporting them.
- Keep model loading and resource resolution inside trusted Rust code.
- Avoid exposing backend-specific device identifiers to remote content.
- Disable unnecessary navigation and remote content in the desktop WebView.

## 11. Frontend technology choice

A practical default is:

```text
Tauri v2 + Vite + TypeScript + React
```

The architecture does not depend on React. The frontend should remain thin and should not attempt to implement audio work through Web Audio APIs.

## 12. Application shutdown

On window close or explicit quit:

1. Decide whether tray mode keeps the engine active.
2. If quitting, send a bounded engine shutdown command.
3. Fade and stop active routes.
4. Join workers and release streams.
5. Persist configuration after route shutdown or from already validated in-memory state.
6. Exit only after a bounded, observable shutdown sequence.

Do not assume dropping the WebView automatically releases every audio resource cleanly.
